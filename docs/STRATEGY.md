**What the data says beyond the rule**

## POST-TRAINING PLAN (primary focus, user decision 2026-10-04): LoRA SFT on self-generated, test-verified trajectories

**Decision**: the competition is about post-training Gemma 4 31B; we have done none. The paper track only makes sense if it documents a practical implementation of the idea, so the paper will be restructured around this plan (measurement results become supporting evidence). Exp2 stays queued: it picks the best prompt, which is the policy that generates training data.

**Facts established today (no GPU used)**
- Kaggle hosts `google/gemma-4/transformers/gemma-4-31b-it-qat-q4_0-unquantized/2`: the **bf16 weights of the QAT run** (2 shards, 49.8 + 12.8 = 62.5 GB), `Gemma4ForConditionalGeneration`. This is the natural training base; the scorer serves the w4a16-ct quantization of the same QAT model, so an adapter trained on the bf16 weights should transfer (to be verified, not assumed). It also resolves the plan's earlier warning about not re-quantizing.
- Geometry: hidden 5376, 60 layers, 32 heads / 16 KV heads, head_dim 256, MLP 21504, vocab 262144, **sliding window 1024 with only every 6th layer full-attention** (10 of 60), so long-sequence training and serving memory is much smaller than for a dense-attention 31B.
- Kaggle's official image (CPU check, notebook `noobhunterjay/gemma-4-train-env-check`): torch 2.10+cu128, transformers 5.0.0 (the wheelhouse ships 5.13.1), **peft 0.19.1, accelerate 1.13.0, datasets 5.0.0; no trl, no bitsandbytes (the wheelhouse has bitsandbytes 0.46.1 and compressed-tensors 0.15.0.1), no deepspeed or flash-attn**. So plain PEFT plus a custom training loop is available offline; no TRL.
- Adapter format the scorer expects (sample adapters): PEFT LoRA, keys `base_model.model.model.language_model.layers.N.self_attn.{q,o}_proj.lora_{A,B}.weight`, bf16; `adapter_config.json` with `base_model_name_or_path: google/gemma-4-31b-it-qat-w4a16-ct`. HF PEFT on the HF model produces exactly this naming. Limits: unpacked submission < 3 GiB; the scorer serves with `max_loras=8, max_lora_rank=128` (staff say they will size these to the submission; reported fixed in wheelhouse v28 with KV cache about 0.76x).
- Data generation throughput (measured, Exp1): **49 attempts/hour, ~600 attempts per 12 h L4x4 session, ~130 resolved attempts at ~22%**. The binding constraint is unique tasks: 75 usable public tasks (Kaggle-env gold passing); the earlier 104 attempts solved only 16 distinct ones. More diversity needs more tasks (SWE-Pallets-X: 213 locally verified, needs era-aware wheels offline) and several attempts per task.
- Training cost (my arithmetic, **unverified until the spike**): 62.5 GB of weights across 4x24 GB leaves ~7 GB per GPU for activations, LoRA states and logits; with naive layer-sharding (device_map) one GPU is active at a time, ~40 TFLOPs effective gives roughly 100-200 trained tokens/s, so ~1.5M tokens (150 trajectories x 10k) is ~2-4 h per epoch. The 262k-vocab logits need a chunked loss.

**What we expect it to change (hypothesis, not a promise)**: our diagnosis says failures are behavioural (never reaching an edit in ~44% of attempts, loops, incomplete fixes), and rejection-sampled self-distillation is the standard way to shift behaviour toward the efficient, verified trajectories the model already sometimes produces. It will not add knowledge. Gains from ~100-300 trajectories are plausibly modest; the paired evaluation below decides.

**Gated plan (each gate must pass before spending the next; all L4x4 time is on days the user chooses)**
- **G0 (done, no GPU)**: the environment, checkpoint and adapter-format facts above.
- **G1 training/serving spike (one L4x4 session, ~3 h)**: (a) load the bf16 checkpoint across 4 GPUs, LoRA r=16 on q,k,v,o (+MLP if memory allows), gradient checkpointing, 8k-token sequences with chunked loss; record tokens/s and peak memory per GPU; (b) train ~20 steps on the 26 existing trajectories, save a PEFT adapter; (c) serve it through the scorer's own `VllmServer` with the scorer's flags, confirm outputs differ from the base (a "silently zero" LoRA was reported by others), and measure **decode latency and KV cache with the adapter vs without** (96% of task time is model latency, so any LoRA slowdown directly costs solves). *Pass* = >= ~60 trained tokens/s, adapter verifiably active, serving slowdown under ~15%. *Fail* = reshape (shorter sequences, fewer target modules, smaller r) or stop and say so.
- **G2 data**: rollouts with the Exp2-winning prompt on the 75-task pool (several attempts per task), plus SWE-Pallets-X if the wheels can be ported. **Capture the exact vLLM chat requests and responses** (a logging proxy on the server), not only ATIF traces, because training must see the same rendered prompt as inference (Gemma 4 chat template, tool-response formatting including the double JSON escaping, thinking handling, compaction). Filter: verified-resolved only, drop test-touching or looping trajectories, prefer short ones, cap per task so no task dominates; hold out tasks (never trained on) for evaluation.
- **G3 train + evaluate**: SFT with loss on assistant tokens only; evaluate adapter vs base **in one notebook on held-out tasks, paired**, with the same decision-rule style as Exp1/2 and the measured noise floor. Only an adapter that wins on held-out paired evidence and passes the serving checks becomes a submission candidate; a slot is spent only after a Linux compile/serve check of the exact zip (hash-pinned).
- **G4 iterate (expert iteration)** if G3 helps: collect from the adapter policy, retrain. Preference/DPO on same-task win-loss pairs is a candidate second stage; RL is out of reach on this compute.

**Findings from the local pre-flight tests (tiny random Gemma 4 + the real chat template, no GPU quota spent)**: (a) Gemma 4's chat template drops an assistant message's text whenever it carries tool_calls and puts tool responses inside the model turn, so a native rendering is NOT prefix-stable (36 of 63 trajectories failed my prefix check); G1 therefore trains on a flattened plain-text tool protocol, and **G2 must capture the exact vLLM requests/responses** (per-turn prompt/completion pairs, or an append-only history only if the reasoning-persistence fix keeps thoughts in history); (b) the fixed system + task prompt is ~4-5k tokens, so an 8k training window leaves only ~3k for the conversation: use >= 12k; (c) 262k-vocab logits for ~3k label positions used 14 GB on a tiny model, so the loss is computed in 512-position checkpointed chunks (2.2 GB peak); (d) first loss on a random model was 12.49 = ln(262144), confirming the loss/shift code is correct.

**Applying the rule as written**: mechanism-confirmed needs patch-written >= control+6 (A1 got +5, A3 +2, A2 0); candidate needs resolved >= control+3 (A1 +2, A2 0, A3 0). **No arm qualifies — report "no evidence" for any resolve-rate improvement.** Paired sign tests are all non-significant (A1 resolved 2 better/0 worse p=0.50; A1 patch-written 6/1 p=0.12; A3 cap-hit 8 better/3 worse p=0.23). Honest power statement: each task is 3.3 pp on this dev set, so differences of 1-2 tasks are indistinguishable from sampling noise (we already saw identical configs differ by that much between runs), and with only 52 verified tasks total we cannot resolve small effects by re-running; further decisions must lean on mechanism evidence and risk, not on resolve counts.

**Mechanism findings (large, not noise-level — thousands of turns)**:
1. **Thinking-off cuts model latency by ~3x** (mean turn 11.8s -> 3.8s, p90 31s -> 8s) and moves the first edit from 151s to 58s — but it did NOT convert into more patches or fewer cap hits (A2: 19 cap hits vs 18). Reason found in the traces: **without thinking the agent makes 2.8x more tool calls per task (52.7 vs 18.7)**; it substitutes rapid trial-and-error actions for reasoning, so wall time per task barely moves (263s vs 288s). Thinking is not just wasted latency. The speed-up only buys a clear benefit when combined with a prompt that also pushes toward committing (A3: mean 226s/task = -22%, cap hits 13 vs 18, first edit at 42s), at no measured resolve cost (6 vs 6) — a real throughput gain for the 12h budget, though not a score gain.
2. **Edit-early (A1) does what it says in time-to-edit** (median first edit 151s -> 102s; never-edit 14 -> 10; patch-written +5, 6 tasks better vs 1 worse) and had the best resolve count (8 vs 6), but cap hits didn't fall — and it is below our own bar, so it stays a *hypothesis worth a replication*, not a result.
3. **Hypothesis "a hung command burns the cap" was tested and refuted**: only 1/30 tasks per arm has a single command >= 60s (same task in every arm), explaining at most 1 of ~15 cap-hit/no-patch attempts. (Setting `timeout_seconds` to ~60 is still a cheap safeguard for that one task, but it is not the lever.)
4. **What the stuck attempts do** (pooled A0/A1/A3, 37 cap-hit-no-patch vs 20 resolved attempts): stuck attempts spend **34% of calls writing/running repro scripts (resolved: 21%)**, 39% exploring with grep/find/sed/cat, and only **3% on `edit_file` (resolved: 11%)**; exact-duplicate call rate 14% vs 7%. Correlational only, but it points at the next candidate lever: our prompt encourages reproducing the bug first, and stuck attempts over-invest in it.
5. Suggestive but within noise: both thinking-off arms did better on `fastapi` (3/10 and 2/10 vs 1/10 control) and worse on `rich` (3/17 and 4/17 vs 5/17; A1 7/17). n=10/17, so this is a hypothesis for a larger test, not a finding.

**Decision**: no change to the submitted scaffold on the strength of this experiment. The submission baseline (0.12) stands. Candidate next experiments (not yet run): (a) A4 = edit-early + "no reproduction script before your first edit" (targets finding 4), replicated against control on tasks not used here (22 unused `rich` tasks remain, but the pool is rich-heavy — growing the verified pool is the better fix); (b) a latency/time-budget-aware use of A3's -22% task time; (c) grow the verified dev pool first so that effects of ~3 tasks become detectable at all.

## Experiment 1 — scaffold efficiency: make the agent produce a patch before the cap (plan, as launched 2026-10-04)

**Baseline**: submission `56789021` = public 0.12 (~7 of ~60 public-LB tasks). Post-baseline priority (see the reordering rationale below): improve the scaffold before investing in fine-tuning.

**Evidence that motivates it** (all from our 104 real-31B rollout attempts, `data_extra/sft_rollouts/run1_2026-10-01/`; concurrency 4, 6-min cap): 26 resolved, 13 finished-but-failed, **63 hit the time cap — 46 of them with no patch at all**; when the agent finishes on its own it passes 26/39 (67%, flattered by easy pre-filtered tasks). **96% of wall time is model latency** (LLM 26,107s vs tool execution 1,036s over 1,925 turns; median turn 5.1s but mean 13.6s and p90 36s — a heavy tail of long generations, consistent with thinking tokens; community also reports the harness drops thoughts between tool calls, so each turn re-derives its reasoning). The first real edit comes at tool call 10 (median; IQR 6-15) and 44/104 attempts never made one. Also: the analyzer sub-agent was called in only 2/104 attempts and the graph tools 2 times total (`run_command` 1168, `read_file` 675), so ablating either is moot under the current prompt. Caveat: timeout rates were measured at concurrency 4 and overstate the sequential scorer's.

**Hypotheses**: H1 (edit-early prompt): forcing a first real edit by tool call 8 raises the patch-written rate and resolves more tasks, because the working tree is graded as-is at timeout. H2 (thinking off): removing thinking tokens cuts per-turn latency enough to fit more turns in the cap, and the quality loss is smaller than the gain. H3: they combine.

**Design** (`scripts/make_experiment1.py` generates everything; notebook `kaggle_assets/exp1_arms/`; arms dataset `noobhunterjay/gemma4-exp1-arms`): four arms on the SAME 30 dev tasks (all 10 fastapi, all 3 requests, 17 `rich` drawn with a fixed seed from the 39 resolvable — no cherry-picking), one vLLM boot shared by all arms (GPU quota; arm order shuffled with a fixed seed), temperature 0.2, `max_time_minutes: 5` (exactly the submission's settings), `Evaluator.run()` at concurrency 4. Arms differ from control ONLY by: **A0_control** = current `submission/`; **A1_edit_early** = Core Objective block replaced by a hard schedule (locate <=4 calls, first `edit_file` by call 8, partial fix beats none, never revert a plausible fix); **A2_think_off** = `include_thoughts: false` (note: `thinking_budget: 0` is rejected by this harness version's schema despite the README); **A3_edit_think** = A1+A2. Verified before launch: arm diffs are exactly the intended lines (all files normalized to LF so no stray `
` confound), and all four arms pass `compile_submission` locally.

**Metrics**: mechanism — patch-written count and time-cap-hit count (lower variance); outcome — resolved count (paired by task); diagnostics from traces — turn and elapsed time of first real edit, mean per-task seconds.

**Decision rule (fixed in advance)**: with 30 paired tasks the resolved-count comparison can only detect large effects (SD of a paired difference ~ 8-9 pp, i.e. ~+4-5 tasks), so (1) an arm is "mechanism-confirmed" if it raises patch-written by >= 6/30 over control; (2) an arm becomes a submission candidate only if resolved >= control + 3 AND patch-written is not lower on round 1, AND a second round on the same tasks (fresh sampling) keeps resolved >= control; (3) a candidate must then pass a sequential (concurrency 1) check on ~10 tasks for cap-hit behavior under scorer-like latency; (4) only then: `scripts/build_submission_zip.py` + the Linux zip-artifact compile test + the pinned-hash auto-submit path. If thinking-off yields more patches but fewer resolves (>= -3), reject it: speed is not quality. Anything inside the noise band is reported as "no evidence", not as a win.

**Limits stated up front**: concurrency 4 inflates latency vs the sequential scorer (relative comparisons are fair, absolute cap-hit rates are not); dev tasks are pre-filtered to locally gold-verified ones and `rich`-heavy, so absolute resolve rates do not predict the hidden set; n=30 x 1 round is a screen, not proof. Cost: 120 task-runs, est. ~2.5-3 h + ~7 min vLLM boot; the forum reports L4x4 sessions bill ~2x against the weekly GPU quota — check the quota page before launching more runs.

**Reordered next steps after Experiment 1** (rationale: 16 solved tasks are far too few to fine-tune on and any LoRA triggers a reported KV-cache shrink to ~7.6k tokens on the scorer): (1) scaffold efficiency (this experiment); (2) grow the dev/data pool — check how many of the 129 public tasks pass their gold patch in Kaggle's official environment (staff say local failures were our env), upload the 213 verified SWE-Pallets-X tasks; (3) fine-tuning only as an explicit go/no-go after a feasibility spike (can a 31B LoRA be trained on L4x4 at all; does the KV-cache shrink make adapters unusable); (4) start the paper track now (deadline Nov 12) — we already have an empirical study: tool footguns (`search_similar_code` overflow, exact-match-only lookups, async blind spot, output truncation, zip packaging), the 12h-budget analysis, and this experiment.

## Update — ROOT CAUSE of submissions 2-4 failing: PowerShell zip packaging, not the platform (2026-10-03)

**RESULT / CONFIRMED (2026-10-03): submission 5 (`56789021`) scored public 0.12, status COMPLETE, no error** -- our first real score. It was submitted automatically by `scripts/auto_submit_when_open.py` the moment the daily slot reopened (04:04 UTC), with the pinned, Linux-verified POSIX zip. This is a clean controlled comparison: `56780281` (crashed) and `56789021` (ran to completion) contain **byte-identical file contents** (same prompts, tools, sampling, `max_time_minutes: 5`); the only difference is zip entry-name format (backslash via `Compress-Archive` vs POSIX via `build_submission_zip.py`). So the packaging bug was the cause of those crashes, not a platform outage and not anything in the agent. Context for the number: the public leaderboard covers ~half of the ~120 hidden tasks (~60), so one task is worth ~0.017 and 0.12 is ~7 tasks; most public scores sit in 0.06-0.15 and the best seen is higher (e.g. 0.24), so this is a baseline in the community band, not a lead. Our ~20-30% notebook resolve rates were on public tasks pre-filtered to those whose gold patches pass locally (mostly `rich`), so they do not predict the hidden-set score.

`56780281` (submitted ~a day after staff said the GPU outage was resolved) failed with the same "unhandled error". Leaderboard dates showed people who had reported the identical error (e.g. Asim, Noah Sabaj) scoring 0.15 on Oct 2, so the platform was healthy and the fault was in our artifact. **The three crashed submissions (`56717963`, `56752702`, `56780281`) were all built with PowerShell `Compress-Archive`, which stores Windows backslash entry names (`configs\sampling.yaml`). The only zip built with forward slashes (`56682704`) was the only one that ever ran (it timed out).** On the Linux scorer a backslash zip extracts (via Python `zipfile`) as flat files literally named `configs\sampling.yaml`, so `!include prompts/system.md` cannot resolve and compilation dies.

Reproduced on Linux in a Kaggle notebook (`kaggle_assets/zip_test/`, CPU only): backslash zip + Python `extractall` -> `SubmissionValidationError: !include file not found: .../prompts/system.md`; POSIX zip compiles under both Python and `unzip` extraction. (Caveat: CLI `unzip` auto-fixes backslashes, so the failure depends on the scorer extracting with Python; all four real outcomes are consistent with that, but we cannot see the scorer's logs to prove it.)

**Two mistakes of mine worth recording**: (1) my "verification" of the zip used `zipfile.namelist()`, which on Windows silently rewrites `\` to `/` when reading (ZipInfo normalizes `os.sep`), so it could not detect the problem; (2) `unzip -l` had shown the backslash names and I dismissed it as a cosmetic Windows display quirk. Earlier STRATEGY entries claiming the zips were "verified forward-slash" are wrong for that reason. The outage on the forum was real and hit others, but it was *not* what failed our submissions after it was fixed; it may or may not have contributed to `56717963`/`56752702`.

**Fix**: `scripts/build_submission_zip.py` builds the zip with Python `zipfile` using `Path.as_posix()` names (files only, no directory entries, fixed timestamps) and verifies by parsing the zip's *central directory bytes* directly (no normalization): rejects any backslash, requires `agent.yaml` at root, byte-compares every file to `submission/`. **Never package with `Compress-Archive` again.** The fixed zip is ready for the next slot; its content is byte-identical to the validated `submission/` (incl. `max_time_minutes: 5`). Also learned: every notebook validation run (1-8) used a *directory copy* of `submission/`, never the zip artifact -- `kaggle_assets/zip_test/` is the first test of the real artifact.

## Update — real-31B validation notebook (runs 1-5): from ceiling-tuning to root-cause fixes (2026-10-01)

Built `kaggle_assets/notebook/rollout_collection.ipynb` + `kernel-metadata.json` (tracked in git) as a reusable way to run our actual `submission/` scaffold against the real `gemma-4-31b-it-qat-w4a16-ct` on Kaggle's GPU infrastructure *before* spending a submission slot — a notebook run costs personal GPU quota, not a submission slot, and the two are independent (confirmed via `competition_get_submission_limits`). Our own submission scaffold is pushed as a Kaggle Dataset (`noobhunterjay/gemma4-agent-submission`, versioned, gitignored staging copy at `kaggle_assets/submission_dataset/`) and the notebook finds it under `/kaggle/input` by content rather than assuming a mount-path convention.

**Runs 1-4** iterated on `eval_config.yaml`'s per-task ceiling numbers against the same ~20-task subset of the official pool: 4min/15turns/15tools -> 7min/25turns/25tools -> 8min/40turns/40tools. Each looser config reduced but never eliminated ceiling-hits (run 3 at 7/25/25: 20% resolved, but 65% of attempts still hit *some* ceiling), and the pattern by repo was informative: `fastapi` was almost entirely turns-constrained (6/7 attempts hit the cap, often well before using their time budget), while `rich` was a mix of turns- and time-capped. This suggested the ceiling *number* wasn't really the lever that mattered.

**Research pivot**: pulled two public Kaggle notebooks for this competition via the API (`KaggleApi.kernels_pull`) rather than continuing to guess numbers from our own data alone. Finding: of all public notebooks, only two score above 0 on the leaderboard (0.06, 0.12), and **both ship no `eval_config.yaml` at all**, relying on pure harness defaults (60 min / 100 tool calls / 500 turns per task, per `HARNESS_README.md`) — the opposite of our tightening approach. One author explicitly measured: a 5-minute-per-task cap still scored 0.00, and the *entire* ~120-task run finished in ~80 minutes anyway, meaning real per-task time is normally nowhere near any of the ceilings we'd been tuning. This reframes submission `56682704`'s original timeout: it was very likely not "budget too loose" but "agent genuinely stuck/looping on a meaningful fraction of tasks", and no per-task ceiling fixes that if the agent can't tell it already failed.

**Four concrete, previously-unknown root causes found in those notebooks (independently verified where checkable), now fixed in `submission/`**:
1. **`search_similar_code` can silently destroy an already-correct, already-submitted patch.** It returns a matched node's full, *uncapped* source — one community-measured call returned 259,000 characters (~8x the 32,768-token context window) for a single query. That overflow is an uncaught error that discards the task's patch even after `submit_patch()` already succeeded. Fix: removed the tool from both `agent.yaml` and `sub_agents/code_analyzer.yaml` entirely (a hard guarantee it can never be called) rather than relying on a prompt-only warning, which could be dropped by context compaction anyway.
2. **`run_command` keeps only the first 5,000 characters of output, but pytest prints its pass/fail verdict at the END.** Our prompt told the agent to run pytest directly and read the result — meaning on any test with substantial output, the agent could never actually see whether it passed, a plausible direct cause of unproductive retries. Fix: `prompts/system.md`/`analyzer.md` now require redirecting to a file and `tail`ing the end (`pytest ... > /tmp/test_1.log 2>&1; tail -n 30 /tmp/test_1.log`).
3. **The code graph has zero async function/method nodes** (independently confirmed by the community notebook, consistent with our own earlier `calls`-only-edge-type finding). This explains part of why `fastapi` — heavily async — was our worst-performing repo: the graph tools are structurally blind to most of its relevant code. Fix: explicit prompt guidance to skip graph tools entirely for async-heavy code and go straight to `grep`/`read_file`.
4. **`skip_summarization: true` on the analyzer sub-agent forces a wasted turn (a harness nudge) after every single call.** Fix: switched to `false` in `agent.yaml`.

**`eval_config.yaml` removed entirely from `submission/`**, matching both actually-scoring public submissions — harness defaults apply instead (60 min / 100 tool calls / 500 turns, single-command timeout 300s).

**Run 5**: same methodology, 10-task subset of runs 3-4's set (trimmed from 20 given a 60-minute-per-task worst case), testing whether the four root-cause fixes reduce ceiling-hits more effectively than ceiling-tuning did. Also corrects an earlier misdiagnosis in this document: the "Docker copy_from 404" bug write-up above already covers the Windows-only `pathlib.Path('/workspace')` fix; that remains accurate and unrelated to this update, which is about agent-level looping causes, not host-level path bugs.

**Process lesson, adopted going forward**: validate any future `submission/` change against the real 31B via this notebook before spending a submission slot — this was explicit user feedback after the second submission crashed, and the notebook infrastructure built here makes that cheap (GPU quota, not a submission slot) to keep doing.

## Update — Workstream 2: rollout-collection pipeline built; two real bugs found and fixed (2026-10-01)

Started building the rollout-collection driver (`scripts/collect_rollouts.py`) — runs the Workstream 1 scaffold against tasks already confirmed locally resolvable, keeping only trajectories whose resulting patch actually passes (rejection sampling), as raw material for SFT data. It reuses the exact same `run_agent_sandbox` + `verify_task` calls the real scorer's `Evaluator.evaluate_task` uses internally, plus `era_wheels.py`'s per-task wheel resolution for the SWE-Pallets-X pool. Created `submission_drafts/rollout_submission/` (gitignored, not the real submission) as a copy of `submission/` with `temperature: 0.8` instead of `0.2`, for sampling diversity across repeated attempts at the same task.

**Smoke-testing this against LM Studio surfaced two real, previously-misunderstood bugs — one a correction to an earlier (wrong) diagnosis in this doc, one entirely new:**

1. **The "Docker `copy_from` 404" bug from the section below was misdiagnosed.** It is not an intermittent Windows-`npipe` race condition — it is a 100%-deterministic bug, reproduced identically on the exact same file across repeated runs. Root cause: `swegemma.tools.workspace._resolve_workspace_path` (used by `read_file`/`write_file`/`edit_file`) defaults `workspace_root` to `pathlib.Path('/workspace')`. `pathlib.Path` is platform-dependent — on Windows this constructs a `WindowsPath`, and `.resolve()` on a leading-`/` path resolves it against the **current drive** instead of staying a POSIX absolute path (e.g. yields `J:\workspace` instead of `/workspace`). That mangled host-style string is then sent as the *container-side* path to `docker.copy_from`/`copy_to`; Linux treats the backslashes as literal filename characters (not separators), so the container's `readlink -f`/`get_archive` calls look for one bogus file named e.g. `J:\workspace\rich\table.py` under `/workspace` and 404. This is why every `read_file`/`edit_file` call on a task failed for the entire session once it happened — same reason the earlier "clean retry" run's generated diff contained a literal `J:\workspace\...` path (that was this same bug surfacing via `write_file`, not a separate cosmetic artifact). It is still correctly judged **irrelevant to the real scorer** (Linux-only, no drive-letter concept), but it made local Windows testing of `read_file`/`edit_file` fail almost every time, not occasionally.
   - **Fix**: `scripts/collect_rollouts.py` monkeypatches `swegemma.tools.workspace._resolve_workspace_path` at import time (Windows-only, via `sys.platform == "win32"`) with an equivalent implementation built on `pathlib.PurePosixPath` (OS-independent pure string manipulation, no filesystem/drive resolution). Verified fix: `read_file`/`edit_file` on `rich/table.py` went from 100%-reproducible 404s to `status: ok` with real file content, across the same task. This is a workaround in **our own scripts only** — we didn't and can't patch the vendored `swegemma` package used by the real scorer, but the bug can't occur there anyway (Linux has no drives to confuse `/workspace` with).
   - Superseded: `scripts/debug_copy_from.py`'s "inconclusive" investigation — it was testing rapid/idle-gapped `copy_from` calls in isolation, which never hit this bug because it never ran through the real `_resolve_workspace_path` code path with a Windows-style `Path` object.

2. **`search_similar_code`/`get_code_neighbors` are exact-symbol-name lookups, not free-text/semantic search — and this is a real, dataset-wide finding independent of any local infra issue.** Verified directly against the actual data: `embedding_utils.embed()` does a dict lookup by exact key into a `.npz` file whose keys are fully-qualified Python symbol names (e.g. `rich.markdown.TableElement.__init__`), not an on-the-fly encoder call — a natural-language query will essentially never match, always returning `count: 0`. Also verified the code graph's **only real edge type is `calls` (lowercase)**, checked across `rich`, `fastapi`, and `requests` graphs — the tool's own built-in docstring (`edge_type: e.g. 'CALLS', 'DEFINED_IN', 'IMPORTS'`) is misleading for this dataset; passing any of those literally (case included) returns zero neighbors even for a perfectly valid node. Our own `submission/prompts/system.md`/`analyzer.md` told the agent to call `search_similar_code` with "a keyword from the error message" — exactly the wrong usage, and exactly why every graph-tool call in the first two smoke-test attempts returned `count: 0`, forcing the agent to burn its whole turn budget on unproductive queries before ever reading real code.
   - **Fix**: rewrote the graph-tool guidance in `submission/prompts/system.md` and `submission/prompts/analyzer.md` (and synced into `submission_drafts/rollout_submission/`): `search_similar_code`/`get_code_neighbors` require an already-known exact fully-qualified symbol (found via `run_command grep` first if not already given by the problem statement), and `edge_type` must be omitted or exactly `"calls"`.
   - **This fix matters for the real submission too**, not just local testing — the exact-lookup behavior and single edge type are properties of the shipped graph/embedding data itself, so the same dead-end would happen with the real 31B on the real scorer under the old prompt wording.

**Net result after both fixes, re-running the same smoke-test task**: the agent correctly used `run_command grep` to locate `rich/table.py`, `read_file` returned real content, and `edit_file` was attempted repeatedly against real file content (still failed to resolve within the 8-minute budget — E4B kept proposing `old_string` blocks that didn't exactly match, a genuine model-capability limitation of the small local stand-in, not a pipeline defect). **The rollout-collection pipeline itself is now confirmed mechanically correct end-to-end on Windows.** Local LM Studio (E4B) rollouts remain valid only for *pipeline validation*, not real training data — see the caveat in `scripts/collect_rollouts.py`'s docstring: real SFT trajectory collection must run against the actual `gemma-4-31b-it-qat-w4a16-ct` checkpoint (Kaggle L4x4 notebook).

- **Two-phase eval, and it structurally blocks the obvious reward-hacking trick**: Phase 1 (Container A, air-gapped, 4GB RAM/2vCPU) runs the agent; Phase 2 (fresh Container B) applies the patch, then **force-resets any test files or test-runner configs the patch touched** (`conftest.py`, `pytest.ini`, `pyproject.toml`, etc.) back to baseline *before* applying `test_patch` and running pytest. So "pass by editing the test" is not exploitable against the real scorer — but our **own local training/RL harness must replicate this same reset-and-verify behavior**, or the policy could learn a trick during RL that only works against a laxer local setup and fails on the real thing.
- **Concrete default budgets** (overridable per-task via `eval_config.yaml`): 60 min wall-clock, 100 tool calls, 500 turns, 300s per-command timeout, 5,000-char stdout truncation, `read_file` capped at 150 lines/10,000 chars per call. The sample submission ships deliberately tiny budgets (1 min / 10 calls / 50 turns) — that's a cheap-to-run smoke test, not a real config.
- **Agent-loop mechanics matter for prompt design**: the harness nudges a stalled agent (max 3 nudges) with different messages depending on *why* it stalled — including a specific nudge for a truncated `<|tool_call>` tag (i.e., `edit_file`/`write_file` payload too big for `max_output_tokens`). Concrete fix baked into the starter config: keep `thinking_budget: 4096` + `max_output_tokens: 16384`, and instruct the agent to make incremental edits. Also: `thinking_level` must be avoided in favor of `include_thoughts: true` + `thinking_budget` (a LiteLLM param-mapping quirk drops it otherwise).
- **Gotchas to bake into the agent's system prompt directly**: scratch/repro scripts left inside `/workspace` get swept into the submitted patch (`git add -N .` picks up untracked files) — tell the agent to use `/tmp` for scratch files or delete them before `submit_patch()`. Never touch `/workspace/pytest.ini` or `conftest.py`. Delegate file/graph exploration to a read-only `AgentTool` sub-agent with `skip_summarization: true` to keep the root agent's context window from filling up with intermediate `read_file` dumps.
- **`swegemma eval` is the local dev-loop command** (Docker or subprocess sandbox), and it writes exactly the raw material needed for Workstream 2's SFT data pipeline for free: `results/<run>/traces/trace_<instance_id>.json` is a full ATIF-format session trace (thoughts, tool calls, token usage) for every task — this *is* the trajectory-collection mechanism, no separate logging needs to be built.

### Workstream 1 — Agent scaffold v0 (prompt/tool engineering, no training)
Goal: a robust, LoRA-free agent that reliably produces *some* valid patch on every task, submitted within days. This is both the safety-net Final Submission candidate and the trajectory-generation policy for Workstream 2.
- Design the tool-use loop around the graph tools as primary navigation, not raw `run_command`/grep: `search_similar_code` → `get_code_neighbors` → `get_code_subgraph` → `read_file` on the returned symbols → `edit_file`/`write_file` → `submit_patch`. The research agent surfaced a concrete external validation for this pattern (arXiv:2603.27277, "Codebase-Memory"): graph-tool-based navigation reaches ~90% of full-file-dump answer quality at ~10x fewer tokens / 2.1x fewer tool calls — directly relevant under a hard 12h/task-count budget.
- Use `sub_agents`/`AgentTool` sparingly (e.g. one root "coder" agent + one read-only "analyzer" sub-agent) — remember **no parallel calls are supported**, so multi-agent here means sequential delegation, not concurrency/ensembling.
- Add defensive engineering directly informed by the platform issues above: explicit per-task timeouts in `eval_config.yaml`, hard step/turn caps, "no-op" detection (emit `NO_PATCH` cleanly rather than an infinite loop) — every wasted minute here is subtracted from the shared 12h budget across all tasks.
- Iterate against the local 129-task harness before spending a daily submission slot.

### Workstream 2 — Training data generation (the actual differentiator)
Because closed-model distillation is legally/rule-wise unresolved, build the primary data pipeline around what's **already confirmed allowed**: self-generated, test-filtered rollouts from `gemma-4-31b` itself, following the SWE-Gym/R2E-Gym/SWE-RL playbooks the research agent identified:
1. **Expand the task pool beyond the 129.** Reuse the competition's own documented mining pipeline (commit+PR mining → issue linking → fail-to-pass/pass-to-pass verification harness, described in the Data tab) against other permissively-licensed, well-tested Python repos, so training data isn't just the 4 public repos the hidden test set deliberately excludes. This directly targets generalization to the private test repos.
2. **Rejection-sample trajectories** with the Workstream 1 agent (and variations: different temperatures, different graph-tool-usage prompting) against this expanded task pool, run each rollout through the sandbox harness, and **keep only trajectories whose final patch passes fail-to-pass + pass-to-pass** — this is the SFT dataset, mirroring SWE-Gym/R2E-Gym.
3. Flag but defer external-model-assisted data: revisit once the host resolves the "Clarification on distillation from external LLMs" thread; if open-weight-teacher distillation gets a green light, that's the safer variant to use (avoid proprietary-API-ToS risk entirely either way, since it's not necessary given self-generated data is already sanctioned).

### Workstream 3 — SFT then RL post-training
- **SFT**: behavior-clone LoRA on the filtered trajectories from Workstream 2. Critical technical caveat from research: **do not reload the QAT checkpoint with `load_in_4bit`/bitsandbytes** — that re-quantizes it differently from Google's calibration. Load unquantized (bf16), train LoRA on top in bf16, keep the adapter separate, and only merge/re-quantize to the target `w4a16` format at the very end for the submission bundle. Investigate QA-LoRA as an alternative if true end-to-end 4-bit training is preferred, but treat as unverified for this exact compressed-tensors format until tested.
- **RL (GRPO)**: initialize from the SFT checkpoint (not from the raw instruct model — research shows this is materially more reliable), reward = execution-based (pass-to-pass tests passing), on the expanded task pool with a held-out split never used for SFT. Apply known multi-turn-GRPO fixes since vanilla trajectory-terminal-only reward is a known weak point for tool-use credit assignment: DAPO-style loss masking for over-length/timeout rollouts, consider turn-level reward shaping if time allows. Leverage the user's existing GRPO experience here — this is the part of the stack where a custom rollout loop (TRL's stock `GRPOTrainer` was found unsuitable for multi-turn tool use out of the box; `verl`/`verl-agent` are the realistic frameworks) will need the most hand-tuning.
- **Guard against reward hacking explicitly** — documented as a live risk for this exact task type (up to 13.9% exploit rate after RL in one cited benchmark): keep a validation split of tasks the policy never trains against, manually spot-check a sample of "passing" patches for shortcuts (deleting/weakening tests, hardcoding expected outputs, environment tampering), and don't fully trust pass rate alone as the north star during development.
- **Compute allocation**: local 8GB card for tokenization/data-pipeline/prompt-iteration/tiny-scale smoke tests only. Kaggle L4×4 sessions (when queued sessions are available) or TPU v3-8 for actual LoRA SFT/RL runs — confirm early which stack (bitsandbytes/CUDA vs. torchtune/JAX) actually works against this checkpoint format on TPU, since the research agent could not verify this and it changes tooling choice.
