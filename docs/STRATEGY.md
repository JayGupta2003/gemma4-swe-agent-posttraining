## Competition Mechanics (verified from the live Kaggle pages)

- **Task**: post-train `gemma-4-31b-it-qat-w4a16-ct` (fixed, mandatory checkpoint for every agent/sub-agent) into an autonomous agent that fixes real Python issues in 4 repos (`fastapi`, `rich`/Textualize, `requests`, `httpx`). Scored SWE-bench-style: patch applied at `base_commit`, `test_patch` run via pytest, PASS/FAIL, score = % solved.
- **Data provided** (`tasks.jsonl` + `snapshots/` + `graphs/` + `embeddings/` + `wheels/` + `docker/`): 129 public dev tasks with reference `patch`, `test_patch`, full repo snapshot at `base_commit`, a per-task AST call/dependency graph (NetworkX JSON) backing `get_code_neighbors`/`get_code_subgraph`, and 256-dim node embeddings backing `search_similar_code`. Offline pip wheels + a sandbox Docker image let the harness run fully offline. ~120 hidden test tasks come from **private repos** (different from the 4 public ones) — the agent must generalize, not memorize these 4 codebases.
- **Submission**: `submission.zip` (**max 3GB total**) with `agent.yaml` at the root (Google ADK Agent Config format), optional `sub_agents/*.yaml`, `prompts/*.md` via `!include`, `adapters/<name>/` (PEFT LoRA, `adapter_config.json` + `adapter_model.safetensors`), and `skills/<name>/SKILL.md` + `scripts/`/`resources/`. Sandboxed — no path traversal outside the submission root.
- **Agent tools**: `run_command`, `read_file`, `edit_file`, `write_file`, `submit_patch`, `get_status`, plus the 3 graph tools above.
- **Scoring constraints (confirmed by Kaggle staff `Ryan Holbrook` in discussion)**: **no parallel/concurrent LLM calls are supported** on the scorer — multi-sample/ensemble strategies must be sequential and paid for out of the same budget. **12-hour total budget** for all tasks (sandbox setup included, validation excluded); per-task limits are settable via `eval_config.yaml`. Behavior on hitting the 12h wall was still unresolved as of last check — budget conservatively.
- **Rules**: 1 submission/day, up to 2 selected as Final Submissions, teams up to 5. External data/tools allowed if "reasonably accessible" (no excessive cost). **Winning submissions must be released under an OSI-approved open-source license**, including training code — plan for open, reproducible work from day one. Training on **`gemma-4-31b`'s own self-generated trajectories (filtered by your own tests) is explicitly confirmed allowed** by Kaggle staff. Distillation from **proprietary closed models (Claude/GPT/etc.) is unresolved and community members flag it as likely against those providers' ToS** — treat as unsafe until the host rules explicitly; open-weight teacher distillation is an unofficial gray area too (host said an answer is "coming soon").

### Workstream 1 — Agent scaffold v0 (prompt/tool engineering, no training)
Goal: a robust, LoRA-free agent that reliably produces *some* valid patch on every task, submitted within days. This is both the safety-net Final Submission candidate and the trajectory-generation policy for Workstream 2.
- Design the tool-use loop around the graph tools as primary navigation, not raw `run_command`/grep: `search_similar_code` → `get_code_neighbors` → `get_code_subgraph` → `read_file` on the returned symbols → `edit_file`/`write_file` → `submit_patch`. The research agent surfaced a concrete external validation for this pattern (arXiv:2603.27277, "Codebase-Memory"): graph-tool-based navigation reaches ~90% of full-file-dump answer quality at ~10x fewer tokens / 2.1x fewer tool calls — directly relevant under a hard 12h/task-count budget.
- Use `sub_agents`/`AgentTool` sparingly (e.g. one root "coder" agent + one read-only "analyzer" sub-agent) — remember **no parallel calls are supported**, so multi-agent here means sequential delegation, not concurrency/ensembling.
- Add defensive engineering directly informed by the platform issues above: explicit per-task timeouts in `eval_config.yaml`, hard step/turn caps, "no-op" detection (emit `NO_PATCH` cleanly rather than an infinite loop) — every wasted minute here is subtracted from the shared 12h budget across all tasks.
- Iterate against the local 129-task harness before spending a daily submission slot.

### Workstream 2 — Training data generation (the actual differentiator)
Because closed-model distillation is legally/rule-wise unresolved, build the primary data pipeline around what's **already confirmed allowed**: self-generated, test-filtered rollouts from `gemma-4-31b` itself, following the SWE-Gym/R2E-Gym/SWE-RL playbooks the research agent identified:
1. **Expand the task pool beyond the 129.** Reuse the competition's own documented mining pipeline (commit+PR mining → issue linking → fail-to-pass/pass-to-pass verification harness, described in the Data tab) against other permissively-licensed, well-tested Python repos, so training data isn't just the 4 public repos the hidden test set deliberately excludes. This directly targets generalization to the private test repos.
2. **Rejection-sample trajectories** with the Workstream 1 agent (and variations: different temperatures, different graph-tool-usage prompting) against this expanded task pool, run each rollout through the sandbox harness, and **keep only trajectories whose final patch passes fail-to-pass + pass-to-pass** — this is the SFT dataset, mirroring SWE-Gym/R2E-Gym.
3. Flag but defer external-model-assisted data: revisit once the host resolves the "Clarification on distillation from external LLMs" thread; if open-weight-teacher distillation gets a green light, that's the safer variant to use (avoid proprietary-API-ToS risk entirely either way, since it's not necessary given self-generated data is already sanctioned).

### Workstream 3 — SFT then RL post-training
- **SFT**: behavior-clone LoRA on the filtered trajectories from Workstream 2. Critical technical caveat from research: **do not reload the QAT checkpoint with `load_in_4bit`/bitsandbytes** — that re-quantizes it differently from Google's calibration. Load unquantized (bf16), train LoRA on top in bf16, keep the adapter separate, and only merge/re-quantize to the target `w4a16` format at the very end for the submission bundle. Investigate QA-LoRA as an alternative if true end-to-end 4-bit training is preferred, but treat as unverified for this exact compressed-tensors format until tested.
- **RL (GRPO)**: initialize from the SFT checkpoint (not from the raw instruct model — research shows this is materially more reliable), reward = execution-based (pass-to-pass tests passing), on the expanded task pool with a held-out split never used for SFT. Apply known multi-turn-GRPO fixes since vanilla trajectory-terminal-only reward is a known weak point for tool-use credit assignment: DAPO-style loss masking for over-length/timeout rollouts, consider turn-level reward shaping if time allows. Leverage the user's existing GRPO experience here — this is the part of the stack where a custom rollout loop (TRL's stock `GRPOTrainer` was found unsuitable for multi-turn tool use out of the box; `verl`/`verl-agent` are the realistic frameworks) will need the most hand-tuning.
- **Guard against reward hacking explicitly** — documented as a live risk for this exact task type (up to 13.9% exploit rate after RL in one cited benchmark): keep a validation split of tasks the policy never trains against, manually spot-check a sample of "passing" patches for shortcuts (deleting/weakening tests, hardcoding expected outputs, environment tampering), and don't fully trust pass rate alone as the north star during development.
- **Compute allocation**: local 8GB card for tokenization/data-pipeline/prompt-iteration/tiny-scale smoke tests only. Kaggle L4×4 sessions (when queued sessions are available) or TPU v3-8 for actual LoRA SFT/RL runs — confirm early which stack (bitsandbytes/CUDA vs. torchtune/JAX) actually works against this checkpoint format on TPU, since the research agent could not verify this and it changes tooling choice.

### Workstream 4 — Submission cadence & risk management
- With 1 submission/day and only 2 Final Submission picks: burn early slots on (a) unmodified baseline, (b) Workstream-1 scaffold-only agent — both cheap and de-risking. Mid-competition slots track SFT progress. Reserve the two Final Submission picks for **one conservative best-known-good checkpoint** (e.g. scaffold + SFT, no LoRA-serving risk if that's still flaky) and **one best-effort SFT+RL+LoRA checkpoint**, so a LoRA-loading regression on the scorer can't zero out the whole entry.
- Track the Discussion/Discord for host fixes (12h-overrun handling, LoRA loading fixes) — these change what's safe to rely on and should gate whether the "best-effort" pick leans on LoRA at all.
