**Local full-agent smoke testing turned out to be viable via LM Studio, not `transformers serve`.** The 8GB RTX 5070 can't fit even a "small" Gemma 4 variant with `transformers`: the full bf16 `google/gemma-4-E2B-it` checkpoint is 10GB (it's genuinely multimodal — text+vision+audio towers all load even though we only want text), and loading a local GGUF (`gemma-4-E4B-it-Q4_K_M.gguf`, already on disk from LM Studio) via `transformers` dequantizes back to full bf16 during loading (~11GB), OOMing regardless of the small on-disk file size. `transformers serve` also has its own bug for this model: the GGUF's config maps to `Gemma4TextConfig` (`model_type: gemma4_text`) rather than the full multimodal `Gemma4Config`, and `architectures` isn't populated on the text-only sub-config, so the CLI's generic `config.architectures[0]` lookup crashes with `TypeError: 'NoneType' object is not subscriptable`.

**LM Studio sidesteps all of this** — it uses its own llama.cpp-based backend (keeps weights in packed 4-bit form during inference, no dequantization) and exposes a real OpenAI-compatible server, including native tool-calling with correctly-formatted `tool_calls` in the response schema. `swegemma eval` already supports redirecting its model registry to an arbitrary endpoint via `--models-yaml` (see `setup_gemma_model_registry`'s `models.yaml` override path) — [scripts/lmstudio_models.yaml](../scripts/lmstudio_models.yaml) maps our submission's declared `gemma-4-31b-it-qat-w4a16-ct` to LM Studio's `google/gemma-4-e4b` at `http://localhost:1234/v1`. This is a stand-in for iteration speed only (E4B is much weaker than the real 31B) but validates the full harness integration for free.

**Caveat found while doing this — a real bug, but almost certainly Windows-only and irrelevant to the actual Linux-based Kaggle scorer**: in a real, multi-minute agent run (LM Studio backend, full `swegemma eval` loop), every single `read_file`/`edit_file` call on one specific file failed for the entire ~500-600s session with a Docker Engine API 404 (`ctx.docker.copy_from` → `container.get_archive()`), while `run_command`/`search_similar_code`/`get_code_neighbors` on the same container kept working fine throughout. Extensive isolated repro attempts — a from-scratch container running the harness's own full 7-step bootstrap, 40 rapid-fire `copy_from` calls, 12 calls with realistic 15s LLM-latency-like idle gaps — all succeeded 100% of the time; the bug did not reproduce outside the real ADK-driven async agent loop. Best working theory: a race/connection-pool issue specific to Docker Desktop's Windows `npipe` transport under the real Runner's async execution pattern (`get_archive`'s streaming tar response behaving differently than `exec`'s smaller synchronous responses under concurrent/threaded access) — not confirmed, not worth chasing further, since **the real scorer runs on Linux, where `npipe` doesn't exist and this transport-layer bug class cannot occur**. Treat any future local Windows+Docker agent run that gets stuck failing the same tool call repeatedly as this same issue, not a prompt/model problem — don't waste time redesigning the prompt in response to it.

See [scripts/debug_copy_from.py](../scripts/debug_copy_from.py) for the isolation script if this needs revisiting later (e.g. if it turns out to also affect Kaggle's own scoring runs, which would be a much bigger deal and worth reporting to Kaggle staff).

**Verified the "gold patches fail offline" community report directly** ([scripts/check_gold_patches.py](../scripts/check_gold_patches.py) runs every task's reference `patch`+`test_patch` through the real two-phase verification pipeline, no LLM involved). Root cause: **the competition's public `data/wheels/` offline dependency cache is genuinely incomplete**, not a patch-correctness issue. Confirmed missing: `typing_inspection` (a transitive `pydantic` dependency — breaks the import of `fastapi` itself, so it alone was failing ~66 of 67 public fastapi tasks). Fixed by `pip download`-ing the wheel onto our own machine (internet available here, unlike the air-gapped sandbox) and rebuilding `swebench-sandbox:latest`.

**Important gotcha discovered while fixing this**: the harness's `_ensure_container_site_packages` (`swegemma/harness/container_setup.py`) buckets wheels by size — anything **under 16MB is injected into every container's site-packages unconditionally**, regardless of which repo is being tested; only wheels **≥16MB** get selectively injected based on scanning the repo's actual imports. `typing_inspection` is small and safe to add this way (a plain library, nothing pytest-specific). But adding `inline-snapshot` and `dirty-equals` (also small, needed by some other fastapi tests) caused a **regression in unrelated `rich` tasks** — both packages register pytest plugins that pytest **auto-loads for every test run once merely installed**, and `inline-snapshot`'s plugin crashes with an `INTERNALERROR` when it encounters files unrelated to its own snapshot logic. Disabling pytest's global plugin autoload (`PYTEST_DISABLE_PLUGIN_AUTOLOAD`) isn't safe either — the harness's own `pytest-timeout` plugin (and its `-o timeout=0` ini option) depends on autoload too. **Resolution**: reverted `inline-snapshot`/`dirty-equals`/their transitive deps, kept only `typing_inspection`. Net effect after the clean fix: local resolution rate went from **43/129 → roughly 52/129**, concentrated entirely in `fastapi` (1/67 → ~10/67); a further, smaller slice of `fastapi` tasks remains locally unverifiable without a more invasive harness patch (out of scope for now — this only affects the trustworthiness of *our own local dev loop* on the 4 public repos, not the actual hidden-test scoring, which uses a separate, presumably correctly-provisioned wheel bundle for different private repos).

**Also found while investigating**: a host-side stale cache at `%TEMP%\swegemma_sp_cache_v8` (a tar of unpacked wheels, cached by content-independent `cache_name` key) does **not** get invalidated when `data/wheels/` changes — must be manually cleared (`rm -rf` it) after adding/removing wheels, or the fix silently appears not to work. Also: pooled/reused containers keep whatever was previously unpacked into their site-packages (only `/workspace` gets wiped between reuses) — `docker rm -f` everything after changing `data/wheels/`, not just clearing the host cache, or stale results persist.

**The `requests` failures (3/13) are a deliberate, structural limitation, not a gap we can fix**: they need the `pytest-httpbin` plugin (spins up a live local HTTP server via fixtures). Investigating this led straight to `swegemma/harness/container_setup.py`'s own `skip_base_pkgs` set, which explicitly blocklists `pytest_httpbin` from the unconditional-injection bucket (alongside `pytest`, `pluggy`, `pytest_xdist`, etc.) — the competition team evidently hit the exact same pytest-plugin-cross-contamination problem we did and excluded it deliberately. This means httpbin-dependent tests are unsupported by design in this harness, not an oversight — almost certainly true for the hidden test set too, not just our local public-repo copy. Not worth pursuing further; treat these ~10 `requests` tasks (and similar ones we may find later) as structurally unverifiable rather than a bug to fix. (Also learned the hard way: `pip download` grabs Windows wheels by default on this machine — must pass `--platform manylinux2014_x86_64 --python-version 313 --implementation cp --abi cp313 --only-binary=:all:` when a package needs compiled extensions, or you silently ship Windows `.whl` files into a Linux container.)

**Confirmed stable state**: 52/129 locally resolvable (rich 39/48, fastapi 10/67, requests 3/13, httpx 0/1), via the single `typing_inspection` wheel fix only. This is the number to treat as ground truth for local SFT/RL rollout collection and agent-scaffold validation — see `submission_drafts/gold_patch_check/gold_patch_results.json` for the per-task breakdown.

**Practical implication for Workstream 2 (training data)**: don't trust the full 129-task pool uniformly. `rich` (39/48 resolvable, 81%) and `requests` (3/13, 23% — still needs its own investigation, not yet root-caused) are asymmetric; `fastapi` is still mostly unusable locally (~10/67) even after the fix. Any local SFT/RL rollout collection or agent-scaffold validation should either restrict to the repos/tasks confirmed reproducible, or accept that a real chunk of local "failures" are environment artifacts rather than genuine unsolved issues — cross-check against `submission_drafts/gold_patch_check/gold_patch_results.json` before drawing conclusions from local pass rates.

So "pass by editing the test" is not exploitable against the real scorer — but our **own local training/RL harness must replicate this same reset-and-verify behavior**, or the policy could learn a trick during RL that only works against a laxer local setup and fails on the real thing.

The sample submission ships deliberately tiny budgets (1 min / 10 calls / 50 turns) — that's a cheap-to-run smoke test, not a real config.
- **Agent-loop mechanics matter for prompt design**: the harness nudges a stalled agent (max 3 nudges) with different messages depending on *why* it stalled — including a specific nudge for a truncated `<|tool_call>` tag (i.e., `edit_file`/`write_file` payload too big for `max_output_tokens`). Concrete fix baked into the starter config: keep `thinking_budget: 4096` + `max_output_tokens: 16384`, and instruct the agent to make incremental edits. Never touch `/workspace/pytest.ini` or `conftest.py`. Delegate file/graph exploration to a read-only `AgentTool` sub-agent with `skip_summarization: true` to keep the root agent's context window from filling up with intermediate `read_file` dumps.
- **`swegemma eval` is the local dev-loop command** (Docker or subprocess sandbox), and it writes exactly the raw material needed for Workstream 2's SFT data pipeline for free: `results/<run>/traces/trace_<instance_id>.json` is a full ATIF-format session trace (thoughts, tool calls, token usage) for every task — this *is* the trajectory-collection mechanism, no separate logging needs to be built.

### Workstream 1 — Agent scaffold v0 (prompt/tool engineering, no training)

- Design the tool-use loop around the graph tools as primary navigation, not raw `run_command`/grep: `search_similar_code` → `get_code_neighbors` → `get_code_subgraph` → `read_file` on the returned symbols → `edit_file`/`write_file` → `submit_patch`. The research agent surfaced a concrete external validation for this pattern (arXiv:2603.27277, "Codebase-Memory"): graph-tool-based navigation reaches ~90% of full-file-dump answer quality at ~10x fewer tokens / 2.1x fewer tool calls — directly relevant under a hard 12h/task-count budget.

### Workstream 2 — Training data generation (the actual differentiator)

3. Flag but defer external-model-assisted data: revisit once the host resolves the "Clarification on distillation from external LLMs" thread; if open-weight-teacher distillation gets a green light, that's the safer variant to use (avoid proprietary-API-ToS risk entirely either way, since it's not necessary given self-generated data is already sanctioned).

### Workstream 3 — SFT then RL post-training
- **SFT**: behavior-clone LoRA on the filtered trajectories from Workstream 2. Critical technical caveat from research: **do not reload the QAT checkpoint with `load_in_4bit`/bitsandbytes** — that re-quantizes it differently from Google's calibration. Load unquantized (bf16), train LoRA on top in bf16, keep the adapter separate, and only merge/re-quantize to the target `w4a16` format at the very end for the submission bundle. Investigate QA-LoRA as an alternative if true end-to-end 4-bit training is preferred, but treat as unverified for this exact compressed-tensors format until tested.
- **RL (GRPO)**: initialize from the SFT checkpoint (not from the raw instruct model — research shows this is materially more reliable), reward = execution-based (pass-to-pass tests passing), on the expanded task pool with a held-out split never used for SFT. Apply known multi-turn-GRPO fixes since vanilla trajectory-terminal-only reward is a known weak point for tool-use credit assignment: DAPO-style loss masking for over-length/timeout rollouts, consider turn-level reward shaping if time allows. Leverage the user's existing GRPO experience here — this is the part of the stack where a custom rollout loop (TRL's stock `GRPOTrainer` was found unsuitable for multi-turn tool use out of the box; `verl`/`verl-agent` are the realistic frameworks) will need the most hand-tuning.
- **Guard against reward hacking explicitly** — documented as a live risk for this exact task type (up to 13.9% exploit rate after RL in one cited benchmark): keep a validation split of tasks the policy never trains against, manually spot-check a sample of "passing" patches for shortcuts (deleting/weakening tests, hardcoding expected outputs, environment tampering), and don't fully trust pass rate alone as the north star during development.
- **Compute allocation**: local 8GB card for tokenization/data-pipeline/prompt-iteration/tiny-scale smoke tests only. Kaggle L4×4 sessions (when queued sessions are available) or TPU v3-8 for actual LoRA SFT/RL runs — confirm early which stack (bitsandbytes/CUDA vs. torchtune/JAX) actually works against this checkpoint format on TPU, since the research agent could not verify this and it changes tooling choice.
